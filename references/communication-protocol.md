# Communication Protocol

Canonical reference for inter-agent communication in otaman-managed projects.

## Message Bus

All agent communication flows through structured markdown files in the message bus directory, located inside the dedicated otaman folder.

### Directory Structure

```
{project}-otaman/.agents/bus/
├── active/                  # Current messages
│   ├── acks/                # Per-agent acknowledgment files
│   │   ├── {msg-stem}.{agent}.ack
│   │   └── ...
│   └── {timestamp}-{from}-to-{to}-{type}.md
└── archive/
    └── YYYY-MM/             # Archived messages (fully acked + expired)
```

### Message Format

Every message is a markdown file with YAML frontmatter:

```markdown
---
id: {timestamp}-{short-identifier}
from: {sender-agent-name}
to: {recipient-agent-name}    # or "all" for broadcast
priority: normal               # low | normal | high | urgent
type: info                     # see Message Types below
timestamp: 2026-03-06T10:30:00Z
status: pending                # pending | read | resolved (legacy, use ack files)
---

## Subject: {Brief description}

{Message body with details}

**Action required**: {What the recipient needs to do, if anything}
```

### Filename Convention

```
{YYYYMMDDTHHmmSS}-{from-agent}-to-{to-agent}-{type}.md
```

Examples:
- `20260306T103000-backend-agent-to-frontend-agent-contract-change.md`
- `20260306T120000-human-to-all-spec-change-approved.md`
- `20260307T090000-specs-to-all-spec-change.md`

### Message ID Format

```
{YYYYMMDDTHHmmSS}-{short-identifier}
```

The short identifier can be a commit hash, slug, or descriptive tag. Must be unique within the bus.

## Message Types

| Type | When to use | Typical `to` |
|------|-------------|-------------|
| `info` | General announcements, status updates | `all` |
| `question` | Need information from another agent's domain | specific agent |
| `contract-change` | API contract or shared type was modified | affected agents or `all` |
| `spec-change` | Specs were updated (auto-generated by post-commit hook) | `all` |
| `spec-change-request` | Agent proposes a spec change (needs human approval) | `human` |
| `spec-change-approved` | Human approved a spec-change-request | `all` |
| `spec-change-rejected` | Human rejected a spec-change-request | proposing agent |
| `review-request` | Requesting observer review of changes | `all` (observers filter) |
| `task-assignment` | Task mapped to a repo owner (auto-generated by map-tasks) | specific agent |
| `task-complete` | Agent reports task completion (auto-updates tasks.md) | `all` |
| `proposal` | Feature or design proposal for discussion | `all` or specific agent |

## Priority Levels

| Priority | Meaning | Expected response time |
|----------|---------|----------------------|
| `low` | FYI, no action needed | When convenient |
| `normal` | Standard communication | Same work session |
| `high` | Important, should be addressed soon | Before next major task |
| `urgent` | Blocks your work, need immediate response | Immediately |

## Acknowledgment System

Each agent tracks message status independently via ack files.

### Ack File Format

```
.agents/bus/active/acks/{msg-stem}.{agent-name}.ack
```

Contents: `read` or `resolved` (single line).

### Ack Lifecycle

1. Message created in `bus/active/` with `status: pending`
2. Agent reads message -> creates ack file with `read`
3. Agent acts on message -> updates ack file to `resolved`
4. When ALL agents have acked AND message exceeds `max_age_days` -> archived

### Creating Acks

Via CLI:
```bash
otaman ack <msg-stem>                    # marks as resolved (default)
otaman ack <msg-stem> --read             # marks as read only
```

Via file:
```bash
echo "resolved" > .agents/bus/active/acks/{msg-stem}.{agent-name}.ack
```

Via slash command:
```
/otaman:check    # shows pending messages with ack instructions
```

## When to Send Messages

### Always send
- Changed an API contract or shared type -> `contract-change` to affected agents
- Changed database schema -> `contract-change` to backend agents
- Discovered a spec gap during implementation -> `spec-change-request` to `human`

### Send when relevant
- Need information from another repo -> `question` to the owner
- Completed a significant milestone -> `info` to `all`
- Want architecture feedback -> `review-request` to `all`

### Don't send
- Internal changes with no cross-repo impact
- Minor refactoring within your owned repo
- Test file updates (unless test contracts change)

## Broadcast Messages

Messages with `to: all` are broadcast to every agent. Each agent acks independently. Common broadcast types:
- `spec-change` (auto-generated when specs repo commits)
- `spec-change-approved` (human approved a proposal)
- `info` (general announcements)

## Task Completion Actualization

When agents complete tasks from a `task-assignment`, they MUST report completion so `tasks.md` stays in sync.

### How to report completion

Via CLI:
```bash
# Specific tasks:
otaman complete <change-name> --tasks "2.1, 2.3, 3.1-3.5"

# All tasks for a change:
otaman complete <change-name> --all
```

This does two things:
1. Updates `tasks.md` checkboxes (`[ ]` -> `[x]`) in the specs repo
2. Creates a `task-complete` bus message notifying all agents

### task-complete message format

```yaml
---
id: {timestamp}-complete-{change-slug}
from: {agent-name}
to: all
priority: normal
type: task-complete
change: {change-name}
timestamp: {ISO-8601}
status: pending
---
```

### Extra frontmatter field

`task-complete` messages include a `change` field in frontmatter that identifies the OpenSpec change directory name. This enables automated `tasks.md` lookup and update.

### When to send

- After completing one or more tasks from a `task-assignment`
- After completing a full phase of work
- Before starting a new task (report the previous one first)

### Rule

Never ack a `task-assignment` as `resolved` without first reporting completion via `otaman complete`. The task-assignment ack means "I've read it"; the `task-complete` message means "I've done it and tasks.md is updated."

## Cleanup & Archival

- Messages older than `max_age_days` (from `platform.yaml`, default 30) with all agents acked are archived to `bus/archive/YYYY-MM/`
- Archives older than 90 days are deleted
- Cleanup runs automatically during `otaman status` and `otaman init`
- Manual cleanup: `otaman cleanup` (use `--dry-run` to preview)
